## 4. Review of Residual Technical Boundaries & Non-Blocking (`P3`) Observations

### 4.1 Validated Residual Technical Boundaries
1. **High-Cardinality Residential Botnet Clean-IP Login Window (`AUD-D1` Residual):** A residential botnet exhausting `> 120` distinct clean IPs within `300 s` against a single email can temporarily rate-limit unauthenticated logins for that specific target email for up to 5 minutes (`scrypt` backpressure prevents process-wide CPU exhaustion; `/health`, `/readyz`, authenticated sessions, and all other accounts remain unaffected). *Mitigation for public internet SaaS:* Place an edge WAF / Turnstile / WebAuthn challenge in front of `POST /api/auth/login` when `login:acct-clean:<email>` exceeds `20` clean-IP attempts.
2. **Deterrent Watermarking Boundary:** Server-side `pypdfium2` + `Pillow` burned-in pixel watermarks prevent raw PDF extraction (`CV-012`), CSS/DOM overlay removal (`CV-019`), and basic chroma scrubbing (`SEC-005`), **not** analog screen photography or heavy ML inpainting. Honest non-piracy-proof framing is preserved across all docs.
3. **Multi-Replica Master Object Storage (`$CV_DATA_DIR/storage/`):** Relational state, sessions, rate limits, and token redemptions scale across stateless API replicas on PostgreSQL 16, whereas master PDF/audio files currently reside on local POSIX disk (`src/services/storage.js`). Multi-replica write deployments require either a shared POSIX volume (NFS/EFS) or an S3-compatible private object-store adapter.
4. **Subprocess-Per-Render Throughput Envelope:** Bounding concurrent Python workers (`CV_WORKER_MAX_CONCURRENCY=4`, `~82–93 MB` RSS each) caps worst-case render memory to `~370 MB` (`~12–13 pages/sec` cold render throughput per 4-worker node at `~319 ms/page`). Higher-concurrency SaaS tiers can later swap in a persistent warm Python worker pool behind the existing `createPdfEngineAdapter({ runner })` seam without touching routes or authz.
5. **Dedicated Backup Login Role in Production:** `002_database_roles_and_hardening.sql` defines `cv_backup_maint` (`NOLOGIN`). For unattended cron backups in production, operators should create a dedicated `LOGIN` role granted **only** `cv_backup_maint` (rather than reusing `strata_owner`).
